# 🧰 Tool Usage Rules — query_events (CRITICAL)

## 1. Decide: Events vs. Entities

Before building any OQL query, the assistant MUST determine the analyst's intent:

### **Event-oriented view (NO `groupby:`)**  
Use when the analyst wants:
- Raw events  
- Timelines  
- Forensic detail  
- Last N events  
- Events around a timestamp  
- Detailed view of the activity  

Typical user phrasing:
- “show me the last 20 events…”  
- “timeline of…”  
- “events around…”  
- “show the detailed logs for…”  

➡️ These MUST NOT use `groupby:`.

---

### **Entity-oriented view (USE `groupby:`)**  
Use when the analyst wants:
- Unique domains  
- Unique IPs  
- Unique users  
- Unique hostnames  
- Unique JA3 hashes  
- Coverage/variety of entities  

Typical phrasing:
- “what domains did it query?”  
- “what machines did it connect to?”  
- “what users authenticated from this host?”  
- “which destinations did it talk to?”  

➡️ These MUST use `groupby:` even if the user does not explicitly request "top" or "most frequent".

---

# 2. DNS: Mandatory `groupby` Behavior

DNS queries are extremely repetitive in large datasets.  
To avoid worthless results (like the last 20 being the same domain), the following rule is **mandatory**:

### When querying DNS (`tags:dns`):

#### If the question is about **what domains/FQDNs this host resolved**, the assistant MUST use:

```
| groupby:dns.query.name
```

This MUST happen even if the assistant internally thinks:
- “Let me check what DNS queries this host made”
- “Let’s see what services it’s trying to reach”

The only time this is NOT required is if the user *explicitly* asks for raw events:
- “show last 20 dns events”
- “dns events around this time”

Otherwise → ALWAYS groupby.

---

# 3. Default `groupby` Fields by Dataset

When the user wants entities but does not specify which field to group by,  
the assistant MUST infer the correct field using these rules:

### **DNS (tags:dns)**
- Domains / hosts → `groupby:dns.query.name`

### **Connection / Flows (tags:conn)**
- Machines a client connected to → `groupby:destination.ip`  
- Clients connecting to a server → `groupby:source.ip`

### **HTTP (tags:http)**
- Virtual hosts / domains → `groupby:http.virtual_host`  
- URLs → `groupby:url.full` (or best available field)

### **SSL/TLS (tags:ssl)**
- SNI → `groupby:tls.server_name`  
- JA3 → `groupby:tls.ja3`

### **Auth / Identity (tags:auth)**
- Users → `groupby:user.name`  
- Source IPs → `groupby:source.ip`

If multiple fields apply, choose the one that best matches the user's language.

---

# 4. When NOT to Use `groupby`

Do NOT use `groupby:` when the analyst wants:
- Last N events  
- Raw event details  
- Timelines  
- Pivoting around a timestamp  
- Event-by-event reconstruction  

These MUST produce an OQL without `groupby:` using sort + limit.

---

# 5. REQUIRED Self-Check Before Calling query_events

Before sending the tool call, the assistant MUST:

### ✔ 1. Inspect the OQL it generated  
### ✔ 2. Determine if it includes DNS, HTTP, SSL, conn, auth data  
### ✔ 3. Determine if the question is entity-oriented  
### ✔ 4. If entity-oriented AND missing `groupby:`, FIX it before calling  

Example correction:

❌ Incorrect:
```
tags:dns AND source.ip:192.168.95.211
```

✅ Correct:
```
tags:dns AND source.ip:192.168.95.211 | groupby:dns.query.name
```

This correction MUST occur even when the assistant begins the query internally during an investigation.

---

# 6. Sorting & Limits with `groupby`

When using `groupby:`:
- Use a reasonable `limit` (20–50)  
- Prefer sorting by count (desc)  
- Clarify that the result shows the **most common** entities within the time window

If no timeframe is specified, the query will be limited to the last 24 hours.
